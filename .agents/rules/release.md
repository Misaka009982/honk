### CI / releases

本分支由维护者手动构建：`ci.yml`、`release.yml`、`docker.yml`、`weekly.yml`、`reload-benchmark.yml` 均只保留 `workflow_dispatch`。push、PR、标签、Release 发布和定时任务不触发构建。Actions 中选择工作流后点击 Run workflow；Release 选择分支时只上传 artifacts，选择 `v*` / `debug.*` 标签时执行对应发布流程。

独立的 `publish-existing.yml` 同样仅手动触发：维护者先创建指向原构建 SHA 的 `debug.build.<run_id>` 标签，再从 main 填写成功的 main Release 运行编号 `run_id`，复用其完整、未过期产物。历史提交的工作流文件与默认分支不同时，GITHUB_TOKEN 无权创建该标签；开始与发布前均通过 `release-existing.cjs::verifyReleaseTag` 只读校验已有标签（轻量或附注），缺失或指向错误提交时停止，不自动创建或移动。来源验证和产物准备位于 `.github/ci/release-existing.cjs`、`prepare-existing-release.sh`；只提取 A53 所需的 ARM64 musl full 核心和 OpenWrt artifact。核心包内容和内部版本保持原样，仅使用 debug 附件名称兼容安装器。旧构建缺少 LuCI 时，由独立模块补建页面和翻译；新构建已有 LuCI 时整套校验复用。配套 doona 源码取自原提交的固定版本，LuCI 源码附件记录各自来源。发布前保存 `openwrt-release-<run_id>-<run_attempt>` artifact，含完整附件和 SHA256SUMS，保留 7 天并在摘要给出下载链接。此恢复入口提供校验和和原构建链接，不以当前发布提交生成替代原构建的来源证明，也不更新滚动 debug。

`install/openwrt/` 与 `.github/ci/build-openwrt-packages.sh` 是核心打包模块；`install/openwrt/luci/` 与 `.github/ci/build-openwrt-luci.sh` 独立提供 LuCI 共享库、管理页和中文翻译。当前 `OPENWRT_ARCHES` 仅 A53，共生成两个核心包、六个 LuCI 包与配套源码；`scripts/install.sh` 默认安装四个匹配组件，`HONK_LUCI=0` 仅装核心。SDK 固定在 `install/openwrt/sdk.sh`，不改既有 `pins.env`。包内不依赖 v2ray Geo 数据；BTF 优先使用内核自带文件，安装脚本只在缺失时尝试当前固件源的 `vmlinux-btf`。`scripts/install.sh` 默认从 `Misaka009982/honk` 下载，README 指向本仓库产物。使用与验证边界见 [OpenWrt 说明](../../doc/zh/operations/openwrt-packages.md)。

Read with: `AGENTS.md` (Current validation guidance, the workspace gate); `deployment.md` for what the tarballs are for; skill `honk-release` for the tag-to-release sequence.

`.github/workflows/ci.yml` 仅手动触发，现有 PR 路径筛选和标签判断代码保留供后续同步上游。`changes` 在 `ci-report-selection` 中记录本次选择；每次手动运行检查代码与文档，`ebpf` 或 `full` 启用最低内核 eBPF 验证，`full` 另启用近期内核 VM、aarch64、独立 feature 和 x86_64 musl 构建（两个输入默认 true）。`ci-ok` 汇总各 job 的结果。

手动 CI 的 `test` job 在 workspace nextest 前执行用户态路由 golden 用例（`routing::golden::*`，包含解析后的 dae 表达式），并拒绝空测试选择。最低内核 VM 验证由手动输入 `ebpf` / `full` 控制。

The `features` lane also runs the outbound `feature_boundary` integration target and the `honk-tool` suite with `cargo test --no-default-features`, each in a separate Cargo invocation so workspace feature unification cannot hide `rprx`-off cases. Exact nonempty test-list checks require both no-backend regressions before execution; this lane uses plain Cargo rather than nextest.

Workspace lint and nextest explicitly enable `honk-core/native-ui` (which includes `native-api`) so ordinary code CI covers the opt-in native API and embedded UI alongside the default-on Clash API feature; workspace lint also enables `honk-core/udp-bench` and `honk-core/dns-bench` so the `udp_io` and `dns` benchmarks and their harnesses stay compiled and linted, and the `features` lane checks the `udp_io` bench with default features off. Both API listeners still require configuration. The independent `features` lane checks native-only, native+Clash and native-ui builds, requires nonempty authentication/coexistence/embedded-UI selections, and executes native-only HTTP regressions, cross-token isolation and embedded-UI HTTP coverage separately. Native-api-only coverage retains embedded-UI rejection. 当前 Release 使用明确的 `clash-api,ebpf,rprx,native-ui,jemalloc` 功能集，完整原生 API 与两套 UI 均保留。 Every job that enables `native-ui` first runs `ci/fetch-doona.sh`, which downloads both doona editions pinned in `.github/ci/pins.env`, checks their SHA-256 values and exports the standard directory as `HONK_DOONA_DIR`; lite is its `-lite` sibling; the repository vendors no doona files.

The `parser` lane compares config corpus inputs against the pinned dae Go oracle and replays saved fuzz inputs on stable Rust. Its filter covers `honk-config`, `tools/dae-parse`, `fuzz`, corpus source documents and shared build inputs. Dialect-only PRs select parser and docs without selecting workspace code lanes; `ci:full`, failed change detection, pushes and manual CI runs also select parser. Its timeout is eight minutes, and `ci-report-parser` carries conformance/replay counts and the first failing case/path.

`.github/workflows/report.yml` joins stage-1 lane artefacts and per-attempt job results into one marker-bearing bot comment on each matching open pull request. `.github/ci/report/fixtures/ordinary.md` extends the agreed fork layout with parser metrics and anchors the renderer's nine byte-for-byte fixtures.

Host suites use `.config/nextest.toml`'s `ci` profile with per-test timeouts and failure JUnit artifacts. Each VM job BTF-checks both objects, installs pinned geo assets, runs the eBPF-feature core unit suite, and invokes `.github/ci/run-vm-gate.sh floor` or `recent` with its tuple from `.github/ci/pins.env`. The guest runs the real NFQUEUE/nftables netns contract, TC/cgroup link lifecycle, pinned allocator rollback-compatibility test, root-only network tests and exact real SO_MARK socket tests serially without a job container.
The VM executable build explicitly enables `native-api`; the guest requires the nonempty ignored `control::lifecycle::tests::ordinary_shutdown_preserves_live_tcp_until_graceful_completion` selection and runs the ignored `control::lifecycle::tests` suite serially. That test configures one SOCKS5 peer and checks that ordinary shutdown preserves a live TCP request until its final response; it is not a shared-XUDP cycle. This validates the owned mock command loop separately from real hooks/NFQUEUE/routing tests.

`.github/workflows/weekly.yml` 仅手动运行，保留 Weekly 名称便于查找。 It checks floating stable fmt/clippy/nextest and a floating nightly eBPF build, re-downloads every pinned asset without caches to verify its checksum, and runs `cargo audit` for RustSec advisories. Ordinary CI has no weekly schedule; drift failures do not automatically open issues.

Its `public-vless-loopback` job uses the repository-pinned compiler and checksum-pinned official Xray/sing-box executables from `.github/ci/pins.env`. It runs exactly the two public ignored `vless_udp` cases, the ignored library case `official_vision_peers_switch_inner_tls_to_direct` and the ignored `sing_box_shared_source_eim_eif_and_domain_matrix` of `tests/shared_source_sing_box.rs`, each with `rprx` and the nextest CI profile; missing executables or test selections fail. This is an optional manual lane, not a normal PR requirement or the legacy external-mask matrix. Low-port/IPv6 setup is restricted to the ephemeral GitHub-hosted runner; no lab credentials or live hosts are used.

Each of those steps runs `ci/run-exact-ignored-tests.sh <target> <test>...`, which fails unless `nextest list` reports exactly the requested tests as ignored and non-empty before running them.

The independent manual `fuzz` job uses the nightly channel from `crates/honk-ebpf/rust-toolchain.toml` and `CARGO_FUZZ_VERSION` from `pins.env`. It runs `document`, `share_link`, and `lexer` sequentially with two workers, 480 seconds per target, a 10-second input timeout and a 2048 MiB RSS limit. The job has a 40-minute timeout and uploads `fuzz-inputs` on success or failure. It keeps `contents: read` and opens no issues.

`.github/workflows/release.yml` 由维护者手动选择分支或 `v*` / `debug.*` 标签运行。稳定前只编译一个 `aarch64-unknown-linux-musl` full/jemalloc 核心，`cargo test --workspace --no-fail-fast` 在独立主机任务中保留。其他架构、gnu、stock、精简 API 变体和 DEB/RPM/Arch 打包暂时停用；原配方保留供后续扩展。交叉编译仍使用 `ci/zigcc` / `ci/zigcxx` 和 `link-self-contained=no`，主机与 eBPF 工具链继续固定；eBPF 对象必须含 `.BTF`。完整归档附带 doona 两个版本的许可声明，发布附带对应源码。A53 安装包使用 APK v3 和 IPK，LuCI 的 `noarch` / `all` 包配套发布。恢复全量构建时需同时调整 matrix、`targets.sh`、两处产物完整性检查和复用发布的来源选择，不可只扩展一个入口。

`.github/workflows/docker.yml` 仅手动运行，使用指定的已发布版本归档构建 linux/amd64 与 linux/arm64 镜像。`push` 默认为 false；设为 true 时使用工作流的 `GITHUB_TOKEN` 推送到配置的 GHCR 目标，不移动 `latest`。发布 Release 不再触发镜像构建。

A new GHCR package starts private. After the first publication, an organization owner opens the package settings (https://github.com/orgs/daeuniverse/packages/container/honk/settings) and sets its visibility to public, so `docker pull` works without a login; until then only organization members can pull. A successful local build does not verify publication.

当前核心目标为 aarch64，不在 x86_64 runner 中执行目标程序；已有按架构条件控制的 x86_64 启动检查保留供后续扩展。`release.yml` 中的发布仍限于 `v*` / `debug.*` 标签；main 构建使用前述手动恢复发布入口。

Every publication through `release.yml`, formal or Debug, also uploads one `SHA256SUMS` covering all published archives and records a build-provenance attestation for each archive, checked with `gh attestation verify <archive> -R daeuniverse/honk`. The publication job alone holds `id-token: write` and `attestations: write` for that, next to `contents: write`.

### Debug releases

- 推送源码标签（例如 `debug.2026.9.19.score.1`）后，由维护者手动以该标签运行 Release 工作流。推送标签本身不触发构建；手动运行仍执行与正式标签相同的测试和单一 ARM64 musl full 构建。
- 发布前检查 A53 核心归档、核心 APK/IPK、三份 LuCI 组件的双格式包及其源码；缺失、空文件均不能发布。`.github/ci/test-release-artifacts.sh` 覆盖核心归档门禁。
- Each source tag gets its own release, titled with the tag, at `/releases/tag/<tag>`. Earlier Debug releases are never moved or overwritten. Every Debug release is a prerelease with `make_latest: false`; notes identify the source tag, commit and workflow run.
- After the tag release, the workflow force-moves `refs/tags/debug` to the same commit and updates the release titled `Debug` at `/releases/tag/debug` with the same tarballs, so that page and `/releases/download/debug/<asset>` always serve the newest published build. Assets the new build does not have, such as the previous `doona-source-<version>.tar.gz`, are deleted. Downstream pins name the per-tag release, never `debug`. Updating `debug` cannot retrigger `debug.*`.
- Assets keep the fixed `honk-core-debug-<target>[-stock]-{full|clash-api|native-api}.tar.gz` names inside each release. Before the variant suffix existed, the unsuffixed name was the full build; older releases keep that spelling. Re-running the same tag replaces that release's attachments, updates the rolling `Debug` release and prunes again. Retrying only the release job requires all build artifacts to remain available; if any have expired (one-day retention) or been deleted, use **Re-run all jobs** to rebuild the complete set.
- After publishing, the workflow keeps the release it just published plus the nine newest other per-tag Debug releases and deletes the rest; `.github/ci/release-prune.sh` selects that set and `.github/ci/test-release-prune.sh` covers it. Their source tags remain, so `git` can still check them out, but downloads from an older per-tag release stop working; downstream pins should follow the newest Debug tags.
- A pending intermediate run may be superseded by a newer tag. Publication is not transactional: a failed update can leave the tag, notes and assets inconsistent until the release job is re-run.
- All Debug workflows share a concurrency group with `cancel-in-progress: false`, so a new push does not interrupt a running publication. `contents: write` stays confined to the publication job; formal `v*` publication remains independent.

### Release process (standing convention)

- **Versions:** SemVer, `vMAJOR.MINOR.PATCH` with an optional `-alpha.N`, `-beta.N` or `-rc.N` suffix. `[workspace.package] version` in `Cargo.toml` holds the plain `MAJOR.MINOR.PATCH` being released, never a suffix: bump it (and `Cargo.lock`, `crates/honk-ebpf/Cargo.lock` and `fuzz/Cargo.lock`) in a pull request when that number changes, then tag `v<that version>` or `v<that version>-{alpha|beta|rc}.N` on the merged `main` tip once its branch CI is green. Release candidates of one version therefore need no manifest change; `honk --version` reports the tag. The test job runs `.github/ci/check-release-version.sh` and fails a tag that is not SemVer, a manifest version with a suffix, or a tag whose `MAJOR.MINOR.PATCH` differs from the manifest. A tag with a suffix publishes as a prerelease. Tags from before this scheme (`v0.0.1.beta.N`) stay as they are; never move or delete a published tag.
- **Changelog:** before tagging, collect and commit fragments using [changes/README.md](../../changes/README.md#preview-and-release). Merge the dated section for the exact release version into `main`; do not collect fragments during publication.
- **Draft:** 维护者手动以正式标签运行 Release 工作流，成功后创建草稿，发布前对仓库外不可见。
- **Notes:** from a full clone, run `bash .github/ci/release-notes.sh <tag> [assets.md]` to print the draft body in doona's order: an opening sentence, Highlights, Changes, Pairing with doona, Downloads (the assets file) and a link line. It reads that tag's version section from `CHANGELOG.md` and fails if the section is missing. Each change type becomes a collapsed `<details>` block with its bullet count. PR numbers come from the collected changelog, not a publication-time lookup.
    - The body retains the `## Highlights` placeholder for the maintainer and the full-changelog comparison link.
    - `## Pairing with doona` links the embedded UI release from the tag's `.github/ci/pins.env`.
    - The release workflow appends `## Downloads` from `.github/ci/release-assets.sh` without changing the archive explanations.
- **Publish:** the maintainer replaces the Highlights comment with three to five bullets, keeps the generated entries and PR references unchanged (fix a wrong entry in `CHANGELOG.md` instead), checks the assets against the build, then publishes with `gh release edit <tag> --repo daeuniverse/honk --draft=false` or **Publish release** in the web UI.
- **doona:** after publishing, attach this release's builds to the doona release named in `.github/ci/pins.env` and update that release's Pairing section, as doona's [release versions](https://github.com/Zakkaus/doona/blob/main/CONTRIBUTING.md#release-versions) describe.

- **Deployment:** after tagging, use the canonical musl jemalloc gateway tarball. Note development/manual `scp` deployments in the PR/issue of record when they differ from release artifacts.
